# 01. 问题分析与方案选择

## 1. 问题背景

### 1.1 当前架构现状

```
┌─────────────────────────────────────────────────────────────────┐
│                      单服务器架构                                │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │                    Backend Service                        │  │
│  │                    (FastAPI + Agent)                      │  │
│  └──────────────────────────────────────────────────────────┘  │
│                              │                                  │
│                              ▼                                  │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │                   Docker Containers                       │  │
│  │  ┌─────────┐  ┌─────────┐  ┌─────────┐                  │  │
│  │  │ User A  │  │ User B  │  │ User C  │  ...             │  │
│  │  │ Thread1 │  │ Thread1 │  │ Thread1 │                  │  │
│  │  └─────────┘  └─────────┘  └─────────┘                  │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                 │
│  问题：容器内启动的 Web 服务如何让外部访问？                      │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 1.2 核心问题

| 问题 | 描述 | 风险等级 |
|------|------|----------|
| **端口冲突** | 多用户同时使用相同端口（如 8080） | 高 |
| **外部访问** | 容器内服务无法从外部直接访问 | 高 |
| **资源限制** | 可能被滥用（挖矿、DDoS 等） | 中 |
| **安全隔离** | 用户间网络隔离不完善 | 中 |
| **服务发现** | 如何知道用户启动了什么服务 | 低 |

### 1.3 当前代码分析

**现有隔离机制 (`src/docker_sandbox.py`)**：

```python
# 已有的隔离措施
- CPU 限制: cpu_quota=int(settings.DOCKER_CPU_LIMIT * 100000)
- 内存限制: mem_limit=settings.DOCKER_MEMORY_LIMIT
- 文件系统隔离: 每个用户独立 workspace 目录
- 容器级别隔离: 每个线程独立容器

# 缺失的措施
- 网络端口映射: 无
- 网络隔离: 容器间可互通
- 进程数限制: 无
- 网络带宽限制: 无
```

## 2. 方案对比

### 2.1 端口访问方案

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **动态端口 + 反向代理** | 自动分配端口，通过子域名访问 | 扩展性好，URL 友好 | 需要泛域名证书 |
| **固定端口范围** | 每用户分配端口范围 | 实现简单 | 扩展性差，端口浪费 |
| **Tunnel 方案** | 类似 ngrok 的隧道 | 无需配置 | 依赖第三方，稳定性差 |
| **仅内部访问** | 不暴露外部 | 最安全 | 用户体验差 |

**选择：动态端口 + 反向代理**

### 2.2 URL 格式方案

| 方案 | 示例 | 优点 | 缺点 |
|------|------|------|------|
| `{port}-{user}.domain` | `8080-user123.preview.com` | 端口清晰 | URL 较长 |
| `{app}-{user}.domain` | `myapp-user123.preview.com` | 可读性好 | 需要命名 |
| `{user}-{port}.domain` | `user123-8080.preview.com` | 用户优先 | 端口不直观 |

**选择：`{port}-{user}.preview.domain`**

### 2.3 服务管理方式

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **自动检测** | 检测容器内监听端口 | 无需用户操作 | 可能误检测 |
| **手动注册** | 用户通过 API 注册 | 精确控制 | 操作繁琐 |
| **混合模式** | 两者结合 | 灵活 | 复杂度高 |

**选择：自动检测优先，支持手动注册**

### 2.4 资源限制方案

| 方案 | 描述 | 优先级 |
|------|------|--------|
| CPU/内存限制 | 已实现 | - |
| PIDs 限制 | 防止 fork bomb | 高 |
| 网络带宽限制 | 防止带宽滥用 | 中 |
| 磁盘 IO 限制 | 防止 IO 阻塞 | 低 |

## 3. 设计决策

### 3.1 技术选型

| 组件 | 选择 | 理由 |
|------|------|------|
| 反向代理 | **Caddy 2.x** | 自动 HTTPS，配置简单，API 支持 |
| 映射存储 | **Redis** | 已有，高性能，支持过期 |
| 容器网络 | **Docker Bridge** | 简单，未来可迁移 K8s |
| SSL 证书 | **Let's Encrypt** | 免费，自动续期 |

### 3.2 为什么选择 Caddy

```
Caddy vs Nginx vs Traefik

┌─────────────┬────────┬────────┬──────────┐
│ Feature     │ Caddy  │ Nginx  │ Traefik  │
├─────────────┼────────┼────────┼──────────┤
│ 自动 HTTPS  │ ✅     │ ❌     │ ✅       │
│ 配置复杂度  │ 低     │ 高     │ 中       │
│ API 支持    │ ✅     │ ❌     │ ✅       │
│ 动态配置    │ ✅     │ 有限   │ ✅       │
│ 学习曲线    │ 低     │ 高     │ 中       │
│ 性能        │ 高     │ 最高   │ 高       │
└─────────────┴────────┴────────┴──────────┘

结论：Caddy 在易用性和功能之间取得最佳平衡
```

### 3.3 扩展性考虑

**当前：单机 Docker**

```
Internet → Caddy → Docker Containers (单机)
```

**未来：Kubernetes 集群**

```
Internet → Ingress → Service → Pods (多节点)
```

设计时预留的扩展点：
- 端口映射抽象层（可替换为 K8s Service）
- 反向代理抽象层（Caddy → Ingress）
- 服务发现机制（Redis → etcd/Consul）

## 4. 风险评估

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 泛域名证书申请失败 | 服务不可用 | 准备备用证书，监控告警 |
| 端口耗尽 | 新服务无法创建 | 端口池管理，自动回收 |
| Caddy 单点故障 | 所有服务不可用 | 高可用部署 |
| 恶意流量攻击 | 资源耗尽 | 限流、WAF |
| 容器逃逸 | 安全风险 | 安全容器（gVisor/Kata） |

## 5. 成功指标

| 指标 | 目标 |
|------|------|
| 端口映射延迟 | < 100ms |
| 服务访问延迟 | < 50ms (代理层) |
| 证书申请成功率 | > 99% |
| 系统可用性 | > 99.9% |
| 单用户最大端口数 | 10 |
